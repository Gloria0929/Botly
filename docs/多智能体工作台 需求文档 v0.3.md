## 1. 背景与目标

### 1.1 背景

市面上出现了 Grok Bot 这类产品：用户像管理团队一样给多个命名的 AI 智能体派活，智能体之间可以交接任务、共享上下文，只在需要决策时才回来找用户。本项目要做一个 Web 版的类似工作台，核心效果一致：

- 一个总指挥智能体接收用户任务，拆解后调度其他智能体干活。
- 多个智能体在同一个群聊里协作，过程对用户可见。
- 高风险动作先暂停，等用户审批后再继续。
- 关闭页面后任务仍在后台运行。

### 1.2 目标用户

- **主要用户**：自带模型 API Key 的个人开发者、研究者、内容创作者，需要把调研、写作、资料整理这类多步骤工作交给 AI 完成。
- **早期规模**：通过邀请码控制，第一版目标是 50 个以内的活跃账号。

### 1.3 第一版成功指标

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| 多步骤任务完成率 | ≥ 70% | 需要 2 个以上子任务的执行中，以「已完成」结束的比例（用户主动停止的不计入分母） |
| 无人值守比例 | ≥ 50% | 除审批和计划确认外，用户没有额外介入的执行比例 |
| 审批响应中位时长 | ≤ 10 分钟 | 用于判断通知是否有效，也决定 Web Push 的优先级 |
| 卡死执行数 | 0 | 扣除等待用户的时间后，超过 2 小时仍没有进入结束状态的执行 |
| 周留存 | ≥ 40% | 注册满 7 天后仍发起过执行的用户比例 |

## 2. 范围

### 2.1 第一版包含

- 通过 API 接入的智能体（每个 Bot = 角色提示词 + 模型 + 工具）。
- 总指挥调度、子任务派发、结果回传；自动模式与逐步确认模式。
- 账号体系：邀请码注册、邮箱登录，用户之间的数据与 API Key 相互隔离。
- 群聊式界面、计划卡片、任务卡片、审批卡片。
- 共享记忆与 Bot 私有记忆。
- 内置工具：网页搜索、网页读取、沙箱内文件读写。
- 后台任务队列；页面内通知中心与浏览器通知。

### 2.2 第一版不包含

- 每个 Bot 一台持久云电脑（已决定不做，统一走 API 接入）。
- 浏览器录制回放、「演示一遍就学会」类能力。
- 团队协作、共享群聊与角色权限（第一版只做独立账号）。
- 浏览器通知以外的审批渠道，如邮件、短信。
- 邮件、日历等真实外部服务的工具接入。
- 计费、套餐与额度管理（第一版由用户自带模型 API Key）。
- 多层委派、子任务并行、执行中插话（见第 16 节）。
- 移动原生 App（先做响应式 Web）。

## 3. 核心概念与术语

全文统一使用以下术语，「会话」一词不再单独使用。

| 术语 | 定义 |
| --- | --- |
| 模型接入（Provider） | 用户配置的一套 OpenAI 兼容接口：名称、base_url、API Key、可用模型、单价（可选）。一个用户可以有多个。 |
| Bot | 有名字、头像、角色提示词、模型（接入 + 模型名）和工具集的智能体。 |
| 总指挥（Supervisor） | 每个群聊有且只有一个总指挥 Bot，额外拥有 `delegate` 工具，负责拆解、派活和汇总。总指挥也是一个 Bot，可以编辑提示词和模型。 |
| 群聊（Chat） | 用户与一组 Bot 的协作空间，含成员、运行模式和限额设置。 |
| 线程（Thread） | 一段消息流。群聊的主消息流是主线程；每个子任务有自己的子线程。 |
| 执行（Run） | 用户发一条消息触发的一次完整处理过程，从开始到给出最终回答、被停止或失败为止。预算与停止都以执行为单位。 |
| 任务（Task） | 一次执行中，总指挥派给某个 Bot 的一项工作，对应一个子线程。 |
| 步骤（Step） | 一次模型调用或一次工具调用，用于用量统计，不设上限。 |
| 审批（Approval） | Bot 调用「需审批」工具前生成的暂停点。 |
| 提问（Question） | Bot 调用 `ask_user` 生成的暂停点，等待用户文字回复。 |
| 记忆（Memory） | 共享记忆（群聊内所有 Bot 可见）与私有记忆（仅某个 Bot 可见）。 |
| 产物（Artifact） | Bot 在沙箱里写出的文件，用户可以查看和下载。 |

## 4. 典型使用场景与主流程

### 4.1 场景示例

用户在「市场调研」群聊里（成员：总指挥、研究员、写手）发送：「调研 3 家国内向量数据库厂商，写一份 1500 字对比报告。」

1. 总指挥判断为复杂任务，发出计划卡片：① 研究员搜索并整理三家资料；② 写手根据资料写报告。
2. 用户点「开始执行」。
3. 研究员在子线程里多次调用网页搜索和网页读取，把资料写入 `research.md`，完成后群聊出现完成卡片。
4. 写手读取 `research.md` 写报告；写入新文件时触发审批，用户收到浏览器通知并批准。
5. 总指挥汇总，在主线程给出最终回答，并附上报告文件。执行结束，通知中心生成「执行完成」通知。

### 4.2 主流程

```
用户发消息 → 创建执行（Run）并入队 → Worker 运行总指挥
   ├─ 简单任务：总指挥直接回答 → 执行完成
   └─ 复杂任务：总指挥发计划卡片 → 等待用户「开始执行」或修改
         → 按计划依次 delegate → 子 Bot 在子线程运行
              ├─ 需审批 / 提问 → 暂停，通知用户 → 用户处理后恢复
              ├─ 逐步确认模式 → 每个子任务完成后暂停，等待「继续」
              └─ 子任务完成 → 结果回写总指挥 → 下一个子任务
         → 总指挥汇总 → 执行完成
   任意时刻：用户点「停止」→ 执行已停止；超出限额 → 执行失败（附原因）
```

## 5. 功能需求

优先级：`P0` 第一版必须有（M1–M5 内交付）；`P1` 第一版后期迭代（v1.x）；`P2` 第二版及以后。

### 5.1 账号体系

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| ACC-01 | `P0` | 邀请码 + 邮箱 + 密码注册；不开放自由注册。密码至少 8 位，只存哈希。 |
| ACC-02 | `P0` | 登录、退出；会话使用 HttpOnly + Secure + SameSite=Lax 的 Cookie，有效期 7 天。 |
| ACC-03 | `P0` | 登录限流：同一邮箱或 IP 连续失败 5 次后锁定 15 分钟。 |
| ACC-04 | `P0` | 邀请码由命令行脚本生成，可设置可用次数与有效期；记录每个邀请码被谁使用。不做管理后台。 |
| ACC-05 | `P0` | 所有业务数据按用户隔离，接口只能访问当前用户的数据；访问他人资源返回 404（不暴露是否存在）。 |
| ACC-06 | `P0` | 首次登录引导：未配置模型接入前，引导用户先完成配置，否则不能发起执行。 |
| ACC-07 | `P1` | 删除账号：删除该用户全部数据（含文件、日志、加密 Key），30 天内可由管理员脚本恢复，之后彻底清除。 |
| ACC-08 | `P1` | 找回密码与邮箱验证（需要接入邮件发送服务）。 |
| ACC-09 | `P2` | 第三方登录（GitHub、Google）。 |

### 5.2 模型接入

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| MOD-01 | `P0` | 用户可创建多个模型接入：名称、base_url、API Key、模型名列表。接口统一为 OpenAI 兼容格式。 |
| MOD-02 | `P0` | 保存时校验：① 连通性；② 所选模型支持流式输出；③ 支持工具调用（function calling）。不支持工具调用的模型不能被选作总指挥，选作普通 Bot 时提示「该 Bot 将无法使用工具」。 |
| MOD-03 | `P0` | API Key 加密存储，保存后前端只显示末 4 位；修改时需要重新输入完整 Key。 |
| MOD-04 | `P0` | 删除模型接入时，如有 Bot 正在使用，必须先改绑或确认把这些 Bot 置为不可用。 |
| MOD-05 | `P1` | 每个模型可填写输入与输出 token 单价，用于费用统计。 |
| MOD-06 | `P1` | 模型接入的 429、超时等错误按附录 A 的重试策略处理，并在用量页展示错误率。 |

### 5.4 群聊与消息

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| CHT-01 | `P0` | 创建群聊：名称、成员 Bot（至少 1 个）、指定 1 个总指挥；可随时增减成员。 |
| CHT-02 | `P0` | 用户消息默认发给总指挥；输入 `@Bot名` 时由该 Bot 直接处理，不经过总指挥拆解，但仍算一次执行，受限额约束。 |
| CHT-03 | `P0` | 同一群聊同一时间只允许一个进行中的执行；执行进行中时输入框可输入，但发送按钮变为「停止」。 |
| CHT-04 | `P0` | 消息流式输出；Bot 处理中在成员栏和消息流显示「正在输入」。 |
| CHT-05 | `P0` | 消息类型：用户消息、Bot 消息、计划卡片、任务卡片、完成卡片、交接提示、审批卡片、提问卡片、工具调用折叠块、系统提示（如限额停止原因）。 |
| CHT-06 | `P0` | 历史群聊列表，按最近活动排序；可重命名、删除群聊（删除需二次确认）。 |
| CHT-07 | `P1` | 从任意一条消息拉出分支线程深入讨论，不打断主线程。 |
| CHT-08 | `P1` | 消息全文搜索。 |

### 5.5 运行模式与调度

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| RUN-01 | `P0` | 自动模式（默认）：子任务完成后由总指挥自动决定下一步，持续执行直到给出最终回答。 |
| RUN-02 | `P0` | 计划卡片：总指挥判断为复杂任务（预计需要 2 个及以上子任务）时，先发计划卡片（步骤、负责 Bot、预期产出），用户可以「开始执行」、编辑步骤后执行，或取消。简单任务跳过计划直接执行。 |
| RUN-03 | `P0` | 计划执行过程中，总指挥可以根据子任务结果调整后续步骤，调整内容以系统提示的形式显示在群聊里。 |
| RUN-04 | `P0` | 逐步确认模式：每个子任务完成后暂停，用户查看结果，点「继续」进入下一步，或输入意见让总指挥调整后继续。在群聊设置和聊天页顶部切换，切换对下一次暂停点生效。 |
| RUN-05 | `P0` | 总指挥通过 `delegate(bot, 指令, 期望产出)` 派活；被派 Bot 在子线程内独立运行，最终结果回写为总指挥的工具结果。 |
| RUN-06 | `P0` | 所有 Bot 都可以调用 `ask_user` 提问：执行暂停，主线程出现提问卡片并标注来源 Bot；用户回复后从暂停处继续。 |
| RUN-07 | `P0` | 停止按钮：随时停止当前执行，语义见 6.1 节。 |
| RUN-08 | `P0` | 每个子任务完成后在群聊生成完成卡片（Bot、耗时、token、结果摘要），不阻塞流程。 |
| RUN-09 | `P0` | 委派深度固定为 1：只有总指挥能派活，子 Bot 没有 `delegate` 工具；子任务串行执行。 |
| RUN-10 | `P0` | 子 Bot 失败（重试后仍失败）时，失败原因回写总指挥，由总指挥决定改派、跳过或结束；同一子任务最多改派 1 次（按计划步骤识别同一个子任务，指令改写不额外获得次数）。 |
| RUN-11 | `P0` | 自动模式下，执行在以下情形停下等待用户：给出最终回答、需审批、Bot 提问、逐步确认暂停、超出限额、Bot 重试后仍失败且总指挥无法处理。 |
| RUN-12 | `P1` | 多个子任务并行执行，总指挥等待全部返回后汇总。 |
| RUN-13 | `P1` | 执行中插话：新消息进入队列，总指挥在下一步开始前读取并调整方向。 |

### 5.6 审批

| 编号 | 优先级 | 需求 |

## 6. 状态机

### 6.1 执行（Run）

| 状态 | 说明 | 可转到 |
| --- | --- | --- |
| 排队中 | 等待 Worker | 运行中、已停止 |
| 运行中 | Worker 正在处理 | 等待用户、已完成、失败、已停止 |
| 等待用户 | 计划确认、审批、提问或逐步确认暂停，不占用 Worker | 排队中（用户处理后重新入队）、失败（审批过期且总指挥无法继续）、已停止 |
| 已完成 | 总指挥给出最终回答 | — |
| 失败 | 超出限额、不可恢复的错误 | — |
| 已停止 | 用户点击停止 | — |

停止语义：

- 正在进行的模型调用立即中断，已经流式输出的内容保留，并标注「已停止」。
- 正在执行的工具调用等待其完成（最长 30 秒），结果写入记录但不再交给模型。
- 已完成的子任务、消息、产物全部保留；进行中的子任务置为「已取消」；待处理的审批与提问置为「已失效」。
- 已停止的执行不能恢复。用户再发消息时开启新的执行，总指挥可以看到之前的上下文。

### 6.2 任务（Task）

`排队中 → 进行中 → 已完成 / 失败 / 已取消`；进行中可以进入「等待审批」或「等待回复」，处理后回到进行中。

### 6.3 审批（Approval）

`待处理 → 已批准 / 已拒绝 / 已过期 / 已失效`（所属执行被停止时为「已失效」）。

## 8. 非功能需求

### 8.1 性能

- 首个 token 的额外延迟（不含模型本身）小于 500 毫秒。
- 任务面板状态更新延迟小于 2 秒。
- 打开有 1000 条消息的群聊，首屏渲染小于 1.5 秒（消息分页加载，每页 50 条）。

### 8.2 容量与并发

- 第一版支持 50 个活跃用户、同时 20 个进行中的执行。
- 单用户同时进行中的执行数见附录 A；Worker 进程数可配置，等待用户的执行不占用 Worker。

### 8.3 可靠性与容错

- 服务或 Worker 重启后，进行中的执行从最近的检查点恢复，不丢失已完成的步骤；Worker 异常退出时，任务在超时后由其他 Worker 接管。
- 模型调用超时或返回格式异常时自动重试（最多 3 次，指数退避）；对 429 按 `Retry-After` 等待；仍失败则标记任务失败并通知总指挥。
- 工具调用必须幂等或有去重键：恢复时节点会重新执行，同一工具调用 ID 只真正执行一次。

### 8.4 安全

- 密钥：API Key 使用对称加密存储，主密钥通过环境变量注入，不进代码仓库和数据库；支持主密钥轮换脚本。日志、错误信息、发给前端的数据都不包含明文 Key。
- 认证：密码只存哈希（argon2 或 bcrypt）；登录限流；所有写接口校验 CSRF（SameSite Cookie + 自定义请求头）。
- 隔离：所有查询都带 user_id 条件，由数据访问层统一加上，并有自动化测试覆盖越权访问。
- 提示词注入：网页读取、文件读取得到的内容作为「不可信数据」标注后再交给模型；`L3` 工具始终需要审批，不受模型输出影响；第一版 Bot 不能写记忆。
- SSRF：网页读取禁止访问内网、回环、云厂商元数据地址，限制重定向次数与响应大小。
- 沙箱：文件操作限定在用户目录，禁止符号链接与路径穿越，有容量配额。

### 8.5 隐私与数据保留

- 模型调用与工具调用日志保留 30 天，之后只保留 token 统计。
- 用户删除群聊时，同时删除其消息、子线程、检查点和沙箱文件。
- 在注册页说明：消息内容会发送给用户自己配置的模型服务商。

### 8.6 可观测性

- 记录每次模型调用和工具调用的输入输出、耗时、token、错误，以执行 ID 串联，便于调试。
- 指标：执行完成率、失败原因分布、平均步数、平均 token、审批响应时长（对应 1.3 节成功指标）。
- 告警：Worker 队列积压超过 5 分钟；扣除等待用户的时间后，执行超过 2 小时仍未结束（仅告警，不自动停止）。

### 8.7 兼容性

- 最新两个大版本的 Chrome、Safari、Edge、Firefox；iOS Safari 16.4+、Android Chrome。
- 浏览器通知依赖浏览器支持与用户授权，不可用时回退到页面内通知中心。

## 9. 技术方案

### 9.1 架构

- 后端：Python + FastAPI；Agent 编排使用 LangGraph（总指挥图 + 各 Bot 子图），不自己手写调度循环。
- 模型接入：统一走 OpenAI 兼容接口，支持自配 base_url，可接多家模型和自建网关。
- 前端：Next.js + Tailwind + shadcn/ui，SSE 接收流式事件。前端只做界面渲染，业务接口全部由 FastAPI 提供。
- 存储：Postgres（业务数据 + LangGraph 检查点）；Redis 负责任务队列与事件广播。
- 队列：Redis + arq。
- 账号：使用成熟库（如 fastapi-users）实现邮箱密码登录与 Cookie 会话，不手写密码逻辑。
- 通知：Web Notifications（P0）；Service Worker + Web Push（P1）。
- 进程：API 与 Worker 分开部署。API 负责收发消息、鉴权和推送；Agent 循环全部在 Worker 里执行。
- 部署：一台云服务器 + Docker Compose（前端、API、Worker、Postgres、Redis、反向代理），第一版足够。

落地约束：

- 前端和 API 必须经过同一个反向代理、使用同一个域名（如 `/api` 转发到 FastAPI），避免 Cookie 跨域与 CORS 问题。
- 反向代理对 SSE 路径关闭缓冲、延长读超时（如 Nginx `proxy_buffering off`、`proxy_read_timeout 1h`），并每 15 秒发送心跳。
- 数据库结构变更使用迁移工具（Alembic）管理。

### 9.2 调度循环

1. 用户消息进入 API，API 创建执行记录并放入 Redis 队列。
2. Worker 取出执行，用线程 ID 从 Postgres 加载 LangGraph 状态。
3. 总指挥图运行：调用模型；若调用 `delegate`，则创建子线程与任务，运行目标 Bot 的子图，结果作为工具结果回写总指挥。
4. 遇到计划确认、`ask_user`、需审批的工具或逐步确认暂停时，调用 `interrupt` 暂停，执行置为「等待用户」并释放 Worker，同时通知用户。
5. 用户处理后，API 把执行重新入队，Worker 用同一线程 ID 从检查点恢复。
6. 每一步检查委派深度与 token 预算；进度事件经 Redis 广播，API 用 SSE 推送给浏览器。
7. 用户点击停止时，API 写入停止标记并广播；Worker 在每个步骤之间和流式输出过程中检查该标记。
8. 设计约束：审批点必须放在有副作用的动作之前，因为恢复时该节点会从头重新执行；有副作用的工具按 8.3 节要求做去重。

### 9.3 流式事件协议

- 每个群聊一个 SSE 连接：`GET /api/chats/{id}/events`。
- 每个事件带递增序号，前端断线重连时带上 `Last-Event-ID`，服务端从 Postgres 补发缺失事件。
- 事件类型：`message.created`、`message.delta`、`message.completed`、`run.status`、`task.status`、`approval.created`、`approval.resolved`、`question.created`、`notification.created`、`usage.updated`。
- 用户级通知另用一个连接：`GET /api/notifications/events`。

## 11. 接口概要

## 13. 验收标准（第一版）

| # | 验收标准 | 关联需求 |
| --- | --- | --- |
| 1 | 用户发出一个需要多步骤的任务，总指挥发出计划卡片；确认后派给至少两个不同 Bot，最终返回汇总结果 | RUN-01、RUN-02、RUN-05 |
| 2 | 两个不同账号的 Bot、群聊、记忆、文件、模型接入互相不可见，直接用 ID 访问返回 404 | ACC-05 |
| 3 | 无效、已用完或已过期的邀请码无法注册，并给出对应提示 | ACC-01、ACC-04 |
| 4 | 调用需审批的工具时，执行暂停并弹出浏览器通知；批准后继续，拒绝后 Bot 能根据原因调整；24 小时未处理自动过期 | APV-01 至 APV-04 |
| 5 | 用户拒绝浏览器通知授权后，审批仍然出现在页面内通知中心 | NTF-04 |
| 6 | 逐步确认模式下，每个子任务完成后暂停，点「继续」才进入下一步 | RUN-04 |
| 7 | 运行中点「停止」，2 秒内停止输出；已完成步骤和产物保留，执行状态为「已停止」 | RUN-07 |
| 8 | token 预算用尽时，执行自动停止并显示原因 | LIM-01、LIM-02 |
| 9 | 任务运行中关闭页面再打开，进度与结果完整可见；Worker 重启后，进行中的执行从最近检查点恢复 | NTF-01、8.3 |
| 10 | 用 `@Bot名` 发送的消息由该 Bot 直接处理 | CHT-02 |
| 11 | Bot 写入的文件出现在文件面板，可以预览和下载；尝试访问沙箱外路径失败 | FIL-01、TOL-03 |
| 12 | 网页读取工具访问 `127.0.0.1`、内网地址被拒绝 | TOL-02 |
| 13 | 单个 Bot 的模型调用失败（如 Key 错误），群聊里出现明确提示，整个执行最终进入结束状态，不会卡死 | RUN-10、8.3 |

## 14. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Bot 之间无限派活或循环调用工具 | 费用失控 | 深度固定为 1，加上 token 预算与用户手动停止 |
| 上下文累积过长 | 成本高、效果下降 | 子线程只把结果摘要回写总指挥；P1 做长对话摘要 |
| 不同模型的工具调用格式差异 | 派活失败 | 保存模型接入时校验工具调用；对常见模型做兼容测试 |
| 模型规划能力不足 | 计划不合理、任务完成率低 | 总指挥提示词迭代；推荐总指挥使用能力较强的模型（见 15.2） |
| 网页内容中的提示词注入 | Bot 执行非预期操作 | 不可信内容标注、`L3` 强制审批、Bot 不能写记忆 |
| LangGraph 学习成本，节点重复执行 | 进度延误、副作用重复 | 只用「总指挥图 + 子 Bot 图」最小子集；工具调用去重 |
| SSE 经代理断流 | 用户看不到进度 | 关闭代理缓冲、心跳、`Last-Event-ID` 补发 |
| 通知覆盖不全 | 审批积压 | 页面内通知中心兜底；监控审批响应时长，决定 Web Push 优先级 |
| 多人使用后的滥用 | 服务器负载 | 邀请码控制规模；单用户并发与沙箱配额 |

## 15. 决策与待确认

### 15.1 已确认的决策

- 需要账号体系，第一版支持多个独立账号，数据按用户隔离。
- 注册方式：邀请码注册，第一版不开放自由注册。
- 模型费用：用户自己接入模型 API（自带 base_url 与 API Key），平台不提供统一额度。
- 审批通知第一版只做浏览器通知（含页面内通知中心）。
- 第一版不接入邮件、日历等真实外部服务。
- 不给每个 Bot 配持久云电脑，统一通过 API 接入。
- 调度循环使用 LangGraph，不自己手写；后端使用 Python + FastAPI。
- 运行模式：默认自动模式，复杂任务先出计划卡片；可切换为逐步确认模式；第一版只做「停止」，不做执行中插话。
- 委派深度为 1，子任务串行执行。
- 先做出第一版，后续功能按第 16 节的节奏推进。

### 15.2 待确认

| 问题 | 建议 | 需在何时确认 |
| --- | --- | --- |
| 第一版推荐（文档与引导中展示）哪些模型？ | 平台不内置默认模型；引导页推荐 2–3 个支持工具调用且较稳定的模型，总指挥建议用能力最强的一档，子 Bot 可用较便宜的模型。具体型号在 M1 用 4.1 节场景实测后决定 | M1 结束前 |
| 网页搜索使用哪家服务？ | 选择一家有免费额度、返回正文摘要的搜索 API，由用户自带 Key | M1 开始前 |
| 共享记忆是用户级还是群聊级？ | 第一版用户级，简单；P1 再评估群聊级 | M4 开始前 |
| 是否需要导出群聊记录（Markdown）？ | 建议作为 P1 | M5 开始前 |

## 16. 后续功能规划

后续功能分三档，每一项写明为什么先不做、什么时候该做，避免第一版过早投入。

| 档位 | 功能 | 为什么先不做 | 什么时候做 |
| --- | --- | --- | --- |
| 第一版后期（P1） | Web Push，关闭页面也能收到提醒 | 需要 Service Worker 与订阅管理，iOS 还要求添加到主屏幕 | 审批响应中位时长超过 10 分钟时 |
| 第一版后期（P1） | 找回密码与邮箱验证 | 需要接入邮件发送服务并处理送达问题 | 开始向更多人开放注册时 |
| 第一版后期（P1） | 子任务并行执行 | 并行会增加状态与预算控制的复杂度 | 串行派活稳定运行之后 |
| 第一版后期（P1） | 执行中插话与改方向 | 需要在运行中安全读取新消息并调整计划 | 只靠停止后重新发起不够用时 |
| 第一版后期（P1） | Bot 模板与一键创建 | 先摸清常用角色，再沉淀模板 | 常用角色稳定之后 |
| 第一版后期（P1） | 用量与费用统计 | 先保证限额能生效，统计可以后补 | 开放给更多人使用时 |
| 第一版后期（P1） | MCP 与自定义 HTTP 工具 | 外部工具带来权限与安全问题 | 内置工具无法满足主要场景时 |
| 第一版后期（P1） | 长对话摘要、记忆候选自动生成 | 先观察真实上下文长度与记忆使用情况 | token 消耗或效果出现明显问题时 |
| 第二版 | 第三方登录 | 与邮箱登录重复，不是必需 | 用户反馈注册麻烦时 |
| 第二版 | 多层委派（子 Bot 再向下派活） | 嵌套越深，费用越难预估、问题越难排查 | 单层派活稳定，且确有复杂拆解需求时 |
| 第二版 | 邮件等其他审批与通知渠道 | 每个渠道都要单独对接和维护 | 浏览器通知覆盖不够时 |
| 第二版 | 邮件、日历等外部服务工具 | 涉及 OAuth 授权和真实副作用 | 有明确的核心使用场景时 |
| 第二版 | 代码执行沙箱 | 安全隔离成本高 | 确实需要 Bot 写代码并运行时 |
| 第二版 | 团队空间、共享群聊与角色权限 | 权限模型复杂，要重做数据隔离 | 出现多人共用同一组 Bot 的真实需求时 |
| 第二版 | 计费、套餐与额度管理 | 第一版由用户自带 Key，不涉及收费 | 决定由平台提供模型额度时 |
| 第二版 | 技能沉淀，把跑通的流程保存为模板 | 需要先积累足够多的真实任务 | 同类任务反复出现时 |
| 暂不规划 | 每个 Bot 一台持久云电脑与浏览器操作 | 成本与运维都很高，API 接入足以支撑第一版 | 出现必须操作网页或本地文件才能完成的核心场景时 |
| 暂不规划 | 移动原生 App | 响应式 Web 已能覆盖 | 手机端使用量明显超过桌面端时 |
