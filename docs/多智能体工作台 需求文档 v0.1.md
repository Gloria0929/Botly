# 多智能体工作台 需求文档

版本 v0.2 · 2026-10-28 · 状态：草案

## 1. 背景与目标

市面上出现了 Grok Bot 这类产品：用户像管理团队一样给多个命名的 AI 智能体派活，智能体之间可以交接任务、共享上下文，只在需要决策时才回来找用户。本项目要做一个 Web 版的类似工作台，核心效果一致：

- 一个总指挥智能体接收用户任务，拆解后调度其他智能体干活
- 多个智能体在同一个群聊里协作，过程对用户可见
- 高风险动作暂停，等用户审批后继续
- 关闭页面后任务仍在后台继续运行

## 2. 范围

### 2.1 第一版包含

- 通过 API 接入的智能体（每个 Bot 就是一套 角色提示词 + 模型 + 工具）
- 总指挥调度、子任务派发、结果回传
- 账号体系：邮箱注册与登录，用户之间的数据与 API Key 相互隔离
- 群聊式界面、任务派发卡片、审批卡片
- 共享记忆与 Bot 私有记忆
- 后台任务队列，以及浏览器通知（审批请求、任务完成、任务失败）

### 2.2 第一版不包含

- 每个 Bot 一台持久云电脑（已决定不做，统一走 API 接入）
- 浏览器录制回放、「演示一遍就学会」类能力
- 团队协作、共享会话与角色权限（第一版只做独立账号，详见第 13 节）
- 浏览器通知以外的审批渠道，如邮件、短信（详见第 13 节）
- 计费、套餐与额度管理（第一版由用户自带模型 API Key）
- 移动原生 App（先做响应式 Web）

## 3. 核心概念

- **Bot**：一个有名字、角色、模型和工具集的智能体。
- **总指挥（Supervisor）**：一种特殊 Bot，拥有派活和向用户提问的工具，负责拆解与汇总。
- **线程（Thread）**：一段对话。群聊是顶层线程，每次派活会生成一个子线程。
- **任务（Task）**：总指挥派给某个 Bot 的一项工作，有状态与结果。
- **审批（Approval）**：Bot 执行高风险动作前，请求用户确认的暂停点。
- **记忆（Memory）**：分共享记忆（所有 Bot 可见）和私有记忆（仅某个 Bot 可见）。

## 4. 功能需求

优先级说明：P0 为第一版必须有，P1 为第一版尽量有，P2 为后续迭代。

### 4.1 Bot 管理

- P0：创建、编辑、删除 Bot，字段包括名字、头像、角色提示词、使用的模型、可用工具。
- P0：模型接入统一为 OpenAI 兼容格式，可配置 base\_url 和 API Key，支持接入多家模型和自建网关。
- P1：Bot 模板（研究员、写手、编码等预设角色），一键创建。
- P2：Bot 的启用、停用与版本回滚。

### 4.2 群聊与消息

- P0：创建群聊，选择成员 Bot，默认由总指挥接收用户消息。
- P0：输入栏支持 @某个 Bot，直接指定它处理。
- P0：消息流式输出，Bot 处理中显示「正在输入」。
- P0：消息类型包括普通消息、任务派发卡、交接提示、审批卡、工具调用折叠块。
- P1：从任意一条消息拉出独立子线程深入讨论，不打断主对话。
- P1：消息搜索与历史会话列表。

### 4.3 调度与任务

- P0：总指挥通过 delegate 工具把任务派给指定 Bot，被派 Bot 在子线程内独立运行，结果回写给总指挥。
- P0：任务状态机：排队中、进行中、等待审批、已完成、失败、已取消。
- P0：Bot 可调用 ask\_user，向用户提问并暂停等待回复。
- P0：用户可以随时取消任务或终止整个会话。
- P1：多个子任务并行执行，总指挥等待全部返回后汇总。
- P1：失败任务的重试与改派给其他 Bot。

### 4.4 审批机制

- P0：工具可标记为「需审批」，调用前暂停并生成审批卡，用户批准后继续，拒绝则把拒绝原因回传给 Bot。
- P0：审批请求同时触发浏览器通知和页面内通知；未处理的审批在任务面板与通知中心集中显示。
- P1：「本会话内始终允许此类操作」的快捷选项。

### 4.5 记忆

- P0：共享记忆（用户信息、项目背景、常用约定）与 Bot 私有记忆分开存储，可在界面查看和编辑。
- P1：任务结束后自动生成摘要并写入相关记忆，写入前可由用户确认。
- P1：长对话自动摘要与截断，控制传给模型的上下文长度。

### 4.6 工具

- P0：内置工具：网页搜索、网页读取、文件读写（沙箱目录内）。
- P1：支持通过 MCP 或自定义 HTTP 接口接入外部工具。
- P2：代码执行沙箱。

### 4.7 后台运行与通知

- P0：任务放入后台队列执行，关闭页面后继续运行，重新打开时恢复显示最新进度。
- P0：页面内通知中心：审批请求、任务完成、任务失败都会生成通知，带未读标记，点击跳转到对应位置。
- P0：浏览器通知（Web Notifications）：用户授权后，页面处于打开或后台标签状态时弹出系统通知，点击通知打开对应审批或任务。
- P0：授权弹窗由用户点击「开启通知」按钮触发，不在打开页面时直接弹出；被拒绝时自动回退到页面内通知中心。
- P1：Web Push（Service Worker + VAPID）：关闭页面后也能收到审批与完成提醒。要求站点使用 HTTPS；iOS 16.4 及以上需先把网页添加到主屏幕并从主屏幕打开。

### 4.8 用量与安全控制

- P0：每个任务设置最大步数、最大委派深度和 token 预算，超限自动停止并提示。
- P0：API Key 加密存储，前端不回显明文。
- P1：按 Bot 和按任务统计 token 用量与费用。

### 4.9 账号体系

- P0：邮箱加密码注册、登录、退出；会话使用 HttpOnly Cookie，密码只存哈希。
- P0：Bot、群聊、消息、任务、记忆和 API Key 全部按用户隔离，接口默认只能访问自己的数据。
- P0：每个用户在设置页维护自己的模型接入（base\_url 与 API Key），加密存储；平台不提供统一的模型额度。
- P0：邀请码注册，第一版不开放自由注册，用邀请码控制早期用户规模与滥用。邀请码由管理员生成，可限制使用次数与有效期；第一版用命令行脚本生成，不做管理后台。
- P1：找回密码与邮箱验证，需要接入邮件发送服务。
- P1：第三方登录，如 GitHub、Google。
- P2：团队空间、共享群聊与角色权限。

### 4.10 运行模式与执行控制

- P0：自动模式（默认）：子任务完成后，由总指挥自动决定下一步，持续执行直到给出最终回答，不需要用户逐步发指令。
- P0：计划卡片：复杂任务开始前，总指挥先发出计划卡片（分几步、每步派给谁），用户点「开始执行」后自动跑完，也可以先修改；简单任务跳过计划，直接执行。
- P0：逐步确认模式：每个子任务完成后暂停，用户查看结果并点「继续」才进入下一步；在群聊设置里切换。
- P0：停止按钮：用户可随时停止当前执行，已完成的步骤与结果保留。
- P0：每个子任务完成后，群聊里生成一张完成卡片，不阻塞流程，用户随时能看到进度。
- P0：自动模式下，执行会在这些情形停下来等用户：总指挥给出最终回答、遇到需审批的工具、总指挥主动提问、超过步数或委派深度或预算上限、Bot 重试后仍然失败。
- P0（建议默认值）：第一版委派深度为 1，只有总指挥可以派活，子 Bot 不能再向下派活；子任务按串行执行。
- P1：执行中插话：用户的新消息进入队列，总指挥在下一步开始前读取并调整方向。

## 5. 界面需求

### 5.1 聊天页（核心页面）

- 采用群聊式布局，人和 Bot 在同一条消息流里。
- 顶部成员栏显示各 Bot 的当前状态：空闲、工作中、等待审批。
- 复杂任务开始前先显示计划卡片，带「开始执行」按钮；总指挥派活后，消息下方挂任务卡片，列出任务、负责 Bot 和状态；页面顶部有「停止」按钮和运行模式切换。
- Bot 之间的交接用灰色系统提示行表示，不占用大篇幅。
- 审批卡片用警示色突出，带「批准」和「拒绝」按钮。
- 工具调用和子任务的详细过程默认折叠，只显示一行摘要。
- 输入栏默认发给总指挥，支持 @Bot。

### 5.2 桌面端与手机端

- 桌面端三栏：左侧群聊与 Bot 列表，中间聊天流，右侧任务面板（展示子任务完整对话和工具调用记录）。
- 手机端：右侧任务面板收进抽屉，左侧列表收进菜单。
- 支持深色模式。

### 5.3 其他页面

- 登录与注册页：邮箱与密码登录、邀请码注册。
- Bot 管理页：列表、创建与编辑表单、模型与工具配置。
- 记忆管理页：共享记忆与各 Bot 私有记忆的查看与编辑。
- 通知中心：审批、完成、失败通知的列表，带未读标记。
- 设置页：模型接入（base\_url、API Key）、默认预算限制、浏览器通知开关。

## 6. 非功能需求

- 性能：首个 token 流式返回的额外延迟（不含模型本身）小于 500 毫秒；任务面板状态更新延迟小于 2 秒。
- 可靠性：服务重启后，进行中的任务可从数据库中的状态恢复，不丢失已完成的步骤。
- 容错：模型调用超时或返回异常格式时自动重试（最多 3 次），仍失败则标记任务失败并通知总指挥。
- 安全：API Key 加密、密码只存哈希、登录限流、工具权限分级、审批不可绕过；Bot 文件操作限定在每个用户独立的沙箱目录内。
- 可观测性：记录每次模型调用和工具调用的输入输出、耗时、token，便于调试。
- 兼容性：最新版 Chrome、Safari、Edge；手机浏览器可正常使用。浏览器通知依赖浏览器支持与用户授权，不可用时回退到页面内通知中心。

## 7. 技术方案（建议）

- 后端：Python + FastAPI；Agent 编排使用 LangGraph（总指挥图 + 各 Bot 子图），不自己手写调度循环。
- 模型接入：统一走 OpenAI 兼容接口，支持自配 base\_url，可接多家模型和自建网关。
- 前端：Next.js + Tailwind + shadcn/ui，SSE 流式推送。
- 存储：Postgres（同时存放 LangGraph 检查点）；Redis 负责任务队列与事件广播。
- 队列：Redis + arq（对异步更友好）。
- 账号：使用成熟库（如 fastapi-users）实现邮箱密码登录与 Cookie 会话，不手写密码逻辑。
- 通知：Web Notifications（P0）；Service Worker + Web Push（P1）。
- 进程：API 与 Worker 分开部署，API 负责收发消息、鉴权和推送，Agent 循环全部在 Worker 里执行。
- 部署：一台云服务器 + Docker Compose（前端、API、Worker、Postgres、Redis、反向代理），第一版足够。

### 7.1 调度循环（逻辑）

1. 用户消息进入 API，API 把任务放进 Redis 队列。
2. Worker 取出任务，用线程 ID 从 Postgres 加载 LangGraph 状态。
3. 总指挥图运行：调用模型；若调用 delegate，则创建子线程与任务，运行目标 Bot 的子图，结果作为工具结果回写总指挥。
4. 遇到 ask\_user 或需审批的工具，调用 interrupt 暂停，任务置为等待并释放 Worker，同时通知用户。
5. 用户批准或回复后，API 把任务重新入队，Worker 用同一线程 ID 从检查点恢复。
6. 每一步检查步数、委派深度和 token 预算；进度事件经 Redis 广播，API 用 SSE 推给浏览器。
7. 设计约束：审批点必须放在有副作用的动作（如发邮件）之前，因为恢复时该节点会从头重新执行。

## 8. 数据模型

- users：id、邮箱、密码哈希、状态、创建时间
- user\_settings：user\_id、模型接入配置（base\_url、加密的 API Key）、预算限制、通知开关
- bots：id、名称、头像、角色提示词、模型配置、工具列表、私有记忆
- threads：id、父线程 id、所属群聊、类型（群聊、子任务、分支）
- messages：id、线程 id、发送者（用户或 Bot）、内容、工具调用、类型、时间
- tasks：id、线程 id、派发者、执行 Bot、描述、状态、结果、预算用量
- approvals：id、任务 id、动作描述、参数、状态（待处理、已批准、已拒绝）、处理时间
- memories：id、范围（共享或 Bot 私有）、内容、更新时间
- notifications：id、user\_id、类型、关联对象、已读状态、时间
- push\_subscriptions：user\_id、浏览器订阅信息、创建时间（Web Push 使用）
- usage\_logs：id、任务 id、Bot id、模型、输入输出 token、耗时
- LangGraph 检查点表：由检查点库自动创建，线程 ID 与 threads.id 对应。

除 users 外，所有表都带 user\_id 字段，接口层统一按当前登录用户过滤。

## 9. 里程碑

- M1（命令行原型）：用 LangGraph 搭总指挥图，加 2 到 3 个角色 Bot，跑通「拆解、派活、执行、汇总」，含步数与深度限制，并用 interrupt 验证审批的暂停与恢复。
- M2（账号与 Web 基础版）：邮箱注册登录与数据隔离、群聊界面、流式输出、任务派发卡片、Bot 管理页。
- M3（可控性）：审批机制、自动与逐步确认两种运行模式、计划卡片、后台队列与恢复、页面内通知中心与浏览器通知、用量统计。
- M4（记忆与工具）：共享与私有记忆、MCP 工具接入、长对话摘要。
- M5（打磨）：Web Push、深色模式、手机端适配、错误提示与空状态。

## 10. 验收标准（第一版）

- 用户发出一个需要多步骤的任务，总指挥能拆解并派给至少两个不同 Bot，最终返回汇总结果。
- 两个不同账号的 Bot、会话和记忆互相不可见。
- 涉及需审批的工具时，任务暂停并弹出浏览器通知；批准后继续，拒绝后 Bot 能据此调整。
- 任务运行中关闭页面再打开，进度与结果完整可见。
- 服务重启后，进行中的任务能从最近的检查点恢复。
- 超出步数、深度或预算上限时，任务自动停止并给出明确提示。
- 单个 Bot 的模型调用失败不会导致整个会话卡死。

## 11. 风险与待确认问题

### 11.1 风险

- Bot 之间互相无限派活，导致费用失控：靠深度、步数、预算三重限制兜底。
- 上下文累积过长，成本高且效果下降：需要尽早做摘要与按线程裁剪上下文。
- 不同模型的工具调用格式差异：统一走 OpenAI 兼容接口，并为每个模型做基础兼容测试。
- 框架学习成本：LangGraph 的图、状态与检查点概念较多，第一版只用「总指挥图 + 子 Bot」的最小子集。
- 通知覆盖不全：用户可能拒绝授权，或浏览器不支持；以页面内通知中心兜底。
- 多人使用后的成本与滥用：模型费用由用户自带的 Key 承担，邀请码控制用户规模；仍需预算上限，防止单个任务失控。

### 11.2 待确认

- 第一版默认使用哪些模型？
- 工具范围：第一版是否需要接入邮件、日历等真实外部服务？

## 12. 已确认的决策

- 需要账号体系，第一版支持多个独立账号，数据按用户隔离。
- 注册方式：邀请码注册，第一版不开放自由注册。
- 模型费用：用户自己接入模型 API（自带 base\_url 与 API Key），平台不提供统一额度。
- 审批通知第一版只做浏览器通知。
- 不给每个 Bot 配持久云电脑，统一通过 API 接入。
- 调度循环使用现成框架 LangGraph，不自己手写；后端使用 Python + FastAPI。
- 运行模式：默认自动模式，复杂任务先出计划卡片；可切换为逐步确认模式；第一版只做「停止」，不做执行中插话。
- 先做出第一版，后续功能按第 13 节的节奏推进。

## 13. 后续功能规划

后续功能分三档，每一项写明为什么先不做、什么时候该做，避免第一版过早投入。

| 档位 | 功能 | 为什么先不做 | 什么时候做 |
| --- | --- | --- | --- |
| 第一版后期（P1） | Web Push，关闭页面也能收到提醒 | 需要 Service Worker 与订阅管理，iOS 还要求添加到主屏幕 | 主流程跑通后，使用者开始漏看审批时 |
| 第一版后期（P1） | 找回密码与邮箱验证 | 需要接入邮件发送服务并处理送达问题 | 开始向更多人开放注册时 |
| 第一版后期（P1） | 子任务并行执行 | 并行会增加状态与预算控制的复杂度 | 串行派活稳定运行之后 |
| 第一版后期（P1） | 执行中插话与改方向 | 需要在运行中安全读取新消息并调整计划 | 只靠停止后重新发起不够用时 |
| 第一版后期（P1） | Bot 模板与一键创建 | 先摸清常用角色，再沉淀模板 | 常用角色稳定之后 |
| 第一版后期（P1） | 用量与费用统计 | 先保证预算上限能生效，统计可以后补 | 开放给多人使用时 |
