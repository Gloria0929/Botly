# Botly 自由群聊改造方案(对标 Grok Bot)

Nov 4, 2026 · @Gloria

Botly 现在的群聊由总指挥统一调度。要改成像真群聊:用户发一句话,成员各自判断要不要说话、互相接话和交接,总指挥不再逐个点名并规定回复。做法是新增「自由群聊」模式,与现有「任务模式」并存,最小版本涉及 5 个模块。

## 一、目标

- 用户发消息后,成员像真人一样自己决定谁回应、回应什么。
- 每个成员有自己的名字、职位、性格和长期记忆。
- 成员之间可以互相 @ 和交接,用自己的话说,不是上级下指令。
- 成本可控:一条消息最多触发多少次发言有硬上限。

不在范围内:真正的自主意识或自主目标、语音、改动现有任务模式。

## 二、现状:为什么像冰冷的机器

| 现象 | 位置 | 影响 |
| --- | --- | --- |
| 一条用户消息只创建一个 Run,由总指挥(或被 @ 的成员)处理 | api/chats.py 的发消息接口 | 其他成员只有被派任务后才能发言 |
| 总指挥提示词规定它只负责拆解和派发,委派只说明目标 | orchestrator.py 的 `_build_system_prompt` | 群里发「大家来开会」,总指挥会逐个点名派任务 |
| 成员提示词要求只完成分配的子任务、不要越界,结果要写成给上级的摘要而不是寒暄 | 同上 | 回复是汇报体,没有个性 |
| Bot 只有 `role` 和 `system_prompt`,没有性格字段 | core/models.py 的 Bot | 人设没有地方放 |
| 成员发言走任务线程,再镜像到主线程(`subtask_live`) | orchestrator.py 的 `model_turn` | 群里看到的是被安排好的回复 |

## 三、参考:Grok Bot 的群聊机制

以下来自 xAI 官方文档 [Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration):

- 一个群放 2 到 6 个 Bot。
- 不 @ 任何人时,由群里的 Bot 自己决定谁回应;@ 某个 Bot 表示由它负责;回复某条 Bot 的消息会定向给它;需要多人时可以 @ 多个;Grok 的 `@everyone`（Botly 中为 `@全员`）用于全员通知,文档建议少用。
- Bot 可以在群里发言,也可以互相交接工作:接收方被唤醒后处理,稍后回复,交接在对话里可见。
- 每个阶段只设一个负责人,并行交接会造成重复工作和噪音。
- Bot 私下发给你或别的 Bot 的消息落在各自的私聊里,不进群。
- 每条 Bot 回复都计入用量,包括群回复和 Bot 之间的消息,所以成员越少越省。
- 没有禁止 Bot 互发消息的开关,靠你的指令约束。

文档没有说明 Bot 如何判断该不该回应,这部分要 Botly 自己设计(见 5.3)。

## 四、验收场景

| 场景 | 期望 |
| --- | --- |
| 发「大家来开会」,不 @ 任何人 | 至少 2 个成员用各自口吻回应;总指挥不点名、不规定内容;发言人数不超过上限 |
| 发「@研究员 查一下……」 | 只有研究员回复,其他人保持安静 |
| 回复研究员的某条消息 | 定向给研究员 |
| 发「@全员 今天下午调整排期」 | 每个成员简短确认或补充,每人最多一次 |
| 与大多数成员职责无关的闲聊 | 大多数成员不发言 |
| 研究员发现需要程序员 | 研究员在群里 @程序员,用自己的话提出请求;程序员回应 |
| 静音开关打开 | 没有成员主动发言,@ 仍然生效 |
| 断线重连 | 发言顺序与刷新前一致,没有丢失或重复的消息 |

## 五、方案设计

### 5.1 群聊模式

`Chat` 增加 `mode`:`task`(现有行为,默认)或 `free`。free 模式下总指挥改为可选的「负责人」(职责见第九节),不再统一接收消息。第一版新建群聊默认 task,自由群聊作为可选项,跑稳后再把新建默认改成 free,老群聊保持 task。成员 2 到 6 个。

### 5.2 成员人设

`Bot` 新增 `persona`(性格、说话风格、口头禅)和 `proactivity`(0 到 1,越高越爱引导,默认 0.5)。`role` 继续当职位用,私有记忆继续沿用。

### 5.3 发言判断:谁来回应

用户发消息且没有 @ 任何人时:

1. 为每个启用的成员建一个轻量 Run(`kind="chime"`),记录触发消息和轮次。
2. 每个成员先做一次很短的判断,只输出 JSON:`speak` 和 `urgency`(0 到 10)。输入是自己的人设、职位、最近约 10 条群消息和 `proactivity`。
3. `speak` 为 false 的直接结束;其余按 `urgency` 从高到低排队。

备选做法是用一次路由调用代替每人判断:更省钱,但更像中心调度。建议先用每人判断,靠截断上下文和限制输出长度控制成本。

判断步骤第一版跟随成员自己的模型,不单独配置;成本明显后再在用户设置里加一个可选的「判断模型」,不填就跟随成员。判断结果解析失败时,被 @ 的成员照常回应,其余成员视为不发言。

### 5.4 发言与接话

1. 按排队顺序依次发言(串行),后发言的成员能看到前面的回复。
2. 每个成员用 peer 提示词(5.6)生成回复;没话说就输出 `[PASS]`,不入库。
3. 某个成员的发言 @ 了同伴,被 @ 的人必须回应;没被 @ 的成员可以再做一次判断(接话轮)。
4. 达到发言人数上限、轮次上限或 token 预算,或没有人想说话时停止。

兜底:没有 @ 任何人的消息,如果所有成员都选择不发言,由负责人回应;没有设负责人时,由判断分数最高的成员回应,保证用户发言不会没人理。

### 5.5 成员之间的协作与交接

- 任何成员都可以在群里 @ 同伴,用自己的话提需求;被 @ 方按 5.4 必须回应。
- 需要长时间干活的交接沿用现有任务线程(`delegate`),但由发起的成员创建,不再由总指挥分配。群里只留一行可见的交接,细节放在任务线程里,和 Grok Bot 把成员间私下消息放在各自私聊的做法一致。
- 每个阶段一个负责人,避免多人认领同一件事,这条写进 peer 提示词。
- 现有的 `can_delegate` 和委派深度限制继续有效。

### 5.6 提示词草稿

peer 提示词,作为第三个分支,与 supervisor、worker 并列:

```text
你是「{name}」,在群聊「{chat}」里担任{role}。
性格与说话方式:{persona}
群里的其他成员:{成员名与职位}。
这是一个真实的群聊,不是任务系统。
- 像同事一样说话:有自己的看法和语气,可以简短,可以开玩笑,不用汇报格式。
- 没有人给你规定台词。你自己决定要不要回、回什么;与你无关或别人已经说清楚了,只输出 [PASS]。
- 想请同伴帮忙,直接在群里 @ 对方,用你自己的话说。被 @ 到时必须回应。
- 不重复别人刚说过的话;可以补充、质疑或接话。
- 需要查资料、写文件时再调用工具,做完在群里用一两句话说结果。
```

判断提示词:

```text
你是「{name}」({role}),性格:{persona},积极度:{proactivity}。
下面是群聊最近的消息。判断你现在要不要发言。
只输出 JSON:{"speak": true 或 false, "urgency": 0 到 10 的整数}
被 @ 到、与你的职责直接相关、或你有重要补充时 speak 为 true;
别人已说清楚、与你无关时 speak 为 false。
```

### 5.7 记忆

沿用共享记忆和私有记忆。可以再加一类 `impression`(对某个成员的印象,例如「研究员做事严谨,但回复偏长」),每次群聊结束后用一次小调用更新,每个成员保留有限条数。第一版可以不做。

### 5.8 成本与防失控

下表的默认值是我的建议,待你确认。

| 参数 | 建议默认值 | 说明 |
| --- | --- | --- |
| 成员上限 | 6 | 与 Grok Bot 一致 |
| 每条用户消息最多发言人数 | 3 | 可配置 |
| 接话轮数 | 2 | 超过后即使有人想说也停止 |
| 判断调用的输出长度 | 约 50 token | 只输出 JSON |
| 单条用户消息的 token 预算 | 沿用 Run 预算 | 超出即停止 |
| 静音 | 群聊开关 | 静音后成员不主动发言,@ 仍然生效 |
| `@全员` | 触发全员判断 | 每人最多发言一次 |

`@全员` 不受每条消息 3 人的上限限制,改为每个成员最多发言一次;这个上限在群聊设置里可调。

### 5.9 前端

- 成员正在输入的提示(新增 `bot.typing` 事件)。
- 输入框支持 @成员、`@全员`,支持对某条成员消息点「回复」来定向。
- 群聊设置:模式、静音、发言人数上限。
- 成员资料里可以填写性格和积极度。

## 六、数据与接口改动

| 模块 | 改动 |
| --- | --- |
| core/models.py 与 Alembic 迁移 | `Chat` 加 `mode`、`max_speakers`、`muted`;`Bot` 加 `persona`、`proactivity`;`Run` 加 `kind`、`trigger_message_id`、`round`。用 Alembic 写迁移,不再往 `_light_migrate` 里加 |
| api/chats.py | `PATCH /chats/{id}` 接受 `mode`、`max_speakers`、`muted`;`POST /chats/{id}/messages` 在 free 模式且没有 @ 时创建 chime Run;支持 `@全员` 和 `reply_to` |
| agent/orchestrator.py | 新增 `role="peer"` 的提示词分支;新增判断步骤和 `[PASS]` 处理;接话轮调度(5.4) |
| worker.py | chime Run 单独计并发配额,不占「每用户并发」名额,也避免被全局上限饿死 |
| core/events.py 与前端 | `bot.typing` 事件;群聊设置界面;`@全员` 和回复交互 |

说明:`model_turn` 的后半部分和委派流程(`start_delegate`)我还没有细读,实现前要先确认哪些能复用。

## 八、风险与前置条件

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 成本倍增 | N 个成员意味着每条消息 N 次判断加多次发言 | 成员上限、发言上限、判断只输出 JSON、静音 |
| 互相接话刷屏 | 可能无限循环 | 轮次上限、冷却、只有被 @ 的人必须回应 |
| 人设漂移 | 长对话后各成员口吻趋同 | 每次调用都带 `persona`,定期人工抽查 |
| 串行发言延迟 | 等待时间变长 | 判断阶段并行、发言阶段串行,显示正在输入 |
| Worker 阻塞与事件表膨胀 | 多个成员同时流式输出会放大这两个问题 | 先落实[代码审查文档](https://claude.ai/artifact/Ud6xNiFWAEZdypyrbmqMZ6)里的 P1、P2、P3 |

## 九、已定的决定

1. 新建群聊默认模式:第一版默认任务模式,自由群聊为可选项;跑稳、看清调用量后再把新建默认改成自由群聊。老群聊保持任务模式。
2. 成员上限 6;普通消息最多 3 人发言,每个群聊可调;`@全员` 不受 3 人限制,每人最多发言一次。
3. 判断模型:第一版跟随成员自己的模型,不单独配置;成本明显后再加用户级的可选「判断模型」,不填就跟随成员。
4. 总指挥保留为可选的「负责人」,只负责两件事:无人发言时兜底回应;需要多人分工时出计划(复用 `propose_plan`)。不再点名,也不规定别人怎么回复。没设负责人时,由判断分数最高的成员兜底。

## 十、实施记录（2026-11-04）

阶段 0–2 已落实。新建和已有群聊默认仍为任务模式；可在新建会话或群聊设置中选择自由群聊。成员资料支持填写性格和积极度，成员面板可设置或取消负责人。

根据用户 2026-11-04 的补充要求，自由聊天采用直接并行回应，删除独立的“成员是否回复”判断步骤，不再预先挑选固定三人或展示思考占位。发送下一条消息无需等待上一条结束。本文 5.3、5.4 的判断与串行描述为原始草案，以本实施记录为准。

实现采用一个 `kind="free"` 主执行管理整条用户消息，成员直接进入独立的回应子执行。没有新的 `chime` 判断执行、JSON 分数或按紧急度排队；旧队列里尚未结束的判断执行直接退休，不再请求模型。回应计入对应用户消息的 token 预算，产物目录按执行隔离。

普通消息优先延续最近互动的成员；没有最近对话对象时，由可选负责人或首位可用成员接话。其他成员收到消息后，有实质补充才直接说一两句话，没有必要就静默。补充发言使用短上下文，不主动执行或重复认领对话对象的任务；需要协作时用 @ 自然联系同伴。接话对象和被 @ 的成员仍可使用工具和任务线程。不同消息、不同成员的回应可以并行进行。

普通消息的默认发言人数上限仍为 3，属于上限而非固定名额；成员在实际输出时原子地占用配额，没有补充时可以只有一位成员回应。接话轮次最多 2 轮，仅由自然的成员 @ 触发，不再进行全员二次判断。静音时普通消息只保存，@ 与定向回复仍生效。`@全员` 直接并行唤醒全体可用成员，每人最多一次，不受普通消息 3 人限制。

实际发言配额、接话队列和已完成轮次均持久化，复用现有 LangGraph 检查点和消息序号。`[PASS]` 不保存、不显示为聊天消息。自由群聊不再为还没开口的成员预先渲染思考气泡；只有实际内容到达时才出现消息，真实的任务执行和等待同伴状态仍可查看。长任务交接复用 `delegate` 和任务线程，完成或失败后交回发起成员。

数据库变更在 Alembic `0012`，升级和重启按现有部署流程执行。阶段 3 的印象记忆、依据反馈自动调整积极度仍待后续设计；共享记忆、私有记忆继续沿用。

## 十一、接话与上下文规则（2026-11-05）

本节替代上一节中“所有成员同时生成普通消息回复”的行为。普通消息先让一个明确的对话对象回应，再由其他成员读取已有回应、按需补充；不引入额外的发言判断模型。

| 场景 | 执行规则 |
| --- | --- |
| 普通消息、连续追问 | 延续用户最近选择的对话对象；补充发言不会改变这个对象。没有对话对象时使用可选负责人或首位可用成员 |
| 同一成员收到多条消息 | 在 Worker 认领锁内按用户消息顺序执行；新一问能看到上一问较晚返回的答案，旧一问不会读到之后的新问题 |
| @ 多人、@全员 | 被明确邀请的同轮成员可并行；不同成员也可同时回应不同消息。@全员 每人只回应一次 |
| 普通补充 | 先读主要回应，再逐个读取前面已完成的补充。可以静默，不凑人数；相同内容不发布，达到人数上限后不再生成额外补充 |
| 用户已发新消息 | 不再启动旧话题的可选补充；正在生成但尚未发布的可选补充也不再输出。已明确请求的回应和实际任务仍正常处理 |
| 成员间接话 | 只有正文行首的 @ 邀请触发接话；普通提及、引用和代码不触发。接话者收到具体来源消息、发起成员和原始用户约束 |
| 执行工作 | 成员可直接用自己的工具；确需同伴执行时使用 delegate。任务结果回到发起成员，已委派的工作不会再因最终消息里的 @ 重复派发 |
| 自由群聊与正式任务 | 讨论、追问直接聊天，不提供计划审批和提问卡片工具；正式计划审批使用任务模式。实际工具操作仍按原有权限审批 |
| 失败与恢复 | 主要接话者无有效输出时尝试其他可用成员，不用固定“收到”冒充模型回复；轮次、队列、配额和来源消息持久化，恢复时不重复发言 |

每条成员回复带有来源消息引用，用户可以分辨它在回答哪一问、回应哪位同伴。排队中的成员不显示成正在工作。静音、发言人数、接话轮次和整条消息的 token 预算继续生效。
